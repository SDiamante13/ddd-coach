# Design specs: #66 scroll-into-view, #68 start over with the last paste

## #66 Keep the newest entry above the composer

**Rule:** follow the conversation only while the visitor is already following it.

- "At the bottom" means the log's last entry was fully visible above the composer before the change (within 48 px). Compute this before the DOM updates.
- Scroll the entry into view when these are added:
  - the visitor's own new entry;
  - a pending entry;
  - a reply or refusal as it arrives.
  Scroll only if the visitor was at the bottom. Their own send always scrolls, since they just acted.
- Use `scrollIntoView({ block: "end" })` on the entry's last element, not the `<li>`, so its buttons (Retry, Copy the conversation, Start a new one) land above the composer.
- Clearance: set `scroll-margin-bottom: var(--composer-reserve)` on `ol[role="log"] > li` and on its buttons. `--composer-reserve` already exists in base.css (`calc(38vh + 11rem)`, 30vh + 12rem at ≤480 px). Measure it against the real composer height at max textarea growth. If it over-reserves, use a ResizeObserver on the form to set `--composer-h` and use that instead.
- If they've scrolled up to read, don't move the view. Show a small "New reply ↓" button pinned above the composer (min 44 px, coach tint); clicking it scrolls to the newest entry. It disappears when they reach the bottom.
- Reduced motion: `behavior: "auto"` (no smooth scroll).
- Focus doesn't move on arrival. For a refusal, the existing `role="alert"` announces it, and its buttons are reachable in tab order right after the alert.

**Checks:**
- At 390 px and 1280 px, send so a refusal arrives: its buttons are clickable without scrolling.
- Scroll up, then let a reply arrive: the view stays put and "New reply ↓" appears.

## #68 Starting over offers the last pasted thread

**What "the last long paste" is:** the most recent user message of 1,000 characters or more, or the most recent paste event into the box of 1,000 characters or more, whichever is newer. Keep it only in browser memory, plus local storage once #5 lands. Nothing goes to the server.

**Clear question (extends #62):**

```
Clear this conversation? The log and history go.
Start the new one with:
  (•) Your pasted thread (7,912 characters, "#booking-split (Slack, sanitized)…")
  ( ) Just your draft ("And what about 48102?")
[Copy first]  [Clear]  [Keep]
```

- Default to the pasted thread when one exists. Show its size and its first line, so she recognises it.
- With no long paste in the conversation, the radio group doesn't appear and today's behaviour stays: the draft is kept.
- If the draft is empty, the options are "Your pasted thread" and "An empty box".
- After Clear:
  - the box holds the chosen text;
  - the count/limit rating (slice 50) applies at once;
  - focus goes to the box;
  - the caret is at the end.
  - Nothing is sent automatically.
- A radio group labelled by the question; each option is a real `<label>`/`<input type="radio">`; 44 px rows.

**Checks:**
- Paste 7.9k, get a reply, type a follow-up, then Start a new one with the default: the box holds the 7.9k thread, not the follow-up.
- A short-message conversation shows no radio group.

## #64 Render slice 3's fixed layout as structure

Prototype: `explore-06/structured.html`, with stills `s1` (complete), `s2` (cut at the cap) and `s3` (off-layout lines and markup). Built on the live tokens and base.css.

**Parse** (line by line; the same parser feeds #6 export and #7 carry-over):
- `Events, in order` → then lines matching `N. (From thread|Guess): text` → an ordered list of `{source, text}`.
- `Words that don't match` → a word line `"word"` → meaning lines `- (From thread|Guess): <Team> [say] <meaning>` → `{word, meanings: [{source, team, meaning}]}`.
- `Question for <role>: <question>` → `{role, text}`.
- Any other line is kept in order as plain text in the same reply. Nothing is ever dropped.

**Render** (DOM text nodes only: `textContent`, never `innerHTML`, so `<img onerror>` or `**bold**` shows as literal text):
- Events as an `<ol>`, each with a source chip. The "Guess" chip is dashed and uses `--color-warn`, so it survives greyscale and screenshots. The word is still there.
- Words as a `<table>` with columns Word, Team, Meaning, Source. The word appears on its first row only, with a heavier rule between words. Meanings are capitalised. Chips don't wrap.
- The question as a card: "Question for the ops lead" in small caps, then the question.
- Cut at the cap: the server trims to the last complete line (slice 3 decision 4). The UI adds a dashed note: "Cut short at the reply length limit. What's above is complete. Ask for the rest to continue."

**Copy and export (#6, from interview 05):** in this order:
1. the settle-by line;
2. the words table;
3. the open questions;
4. the events.

Use the same parsed structure, as HTML for rich-text editors plus a plain-text fallback. Copy everything, not just the table.
